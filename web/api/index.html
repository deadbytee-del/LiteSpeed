LiteSpeed API

Version 0.1 · HTTP, no authentication, JSON for everything under /api.

Overview

The backend is a single stateless fetch(Request) → Response handler. It runs on Node, Cloudflare Workers and any runtime with the Fetch API. GitHub Pages hosts only the frontend; every endpoint below lives on the relay you deploy separately. The frontend finds it automatically (see Deployment).

There are two ways to proxy. In service-worker mode (default) the page's service worker rewrites everything in the browser and uses only /bare/v3/ (and optionally /api/ws) on the relay. In server mode the relay rewrites pages itself under /p/{key}/…; it is the fallback when service workers are unavailable. Both run the same engine.

Proxy URL format

{base}/p/{key}{path}{?query}

key = base64url(origin)      e.g. https://example.com  →  aHR0cHM6Ly9leGFtcGxlLmNvbQ

The upstream origin sits in the first path segment, so relative references inside a page resolve to the right place with no rewriting, and cookies can be scoped per upstream with Path=/p/{key}/. Fragments (#…) never reach the server.

If a root-relative request escapes rewriting (e.g. /static/app.js fired by unhooked script), the backend recovers the upstream from the Referer and answers 307 to the right proxy URL.

Endpoints

GET/api/health

Liveness probe, safe to poll. Always 200 when the service is up.

{ "status": "ok", "name": "litespeed", "version": "0.1.0",
  "runtime": "node v22.22.0", "time": "2026-10-02T01:28:39.278Z", "uptimeMs": 879 }

GET/api/info

Capabilities and limits: features (streaming, cache, rewriteJs, websockets=false, serviceWorkers=false), limits (header timeout, cache item size and TTL) and the configured CORS origins.

GET/api/resolve?url=address

Normalises an address (adds https:// when the scheme is missing), applies the target policy, and returns its proxy URL. 400 for unparseable input, 403 for refused targets.

{ "input": "example.com", "url": "https://example.com/",
  "proxyPath": "/p/aHR0cHM6Ly9leGFtcGxlLmNvbQ/",
  "proxyUrl": "https://api.example.workers.dev/p/aHR0cHM6Ly9leGFtcGxlLmNvbQ/" }

GET/api/go?url=address

302 to the proxy path. Useful for plain links: {base}/api/go?url=https://example.com.

GET/api/ping?url=address

Measures the server-to-upstream round trip with a HEAD (falling back to a one-byte ranged GET). This is the number to use when separating network distance from proxy overhead.

{ "url": "https://example.com/", "status": 200, "ok": true, "upstreamMs": 41.3 }

GET/api/runtime.js

The small client runtime injected into proxied HTML. It hooks fetch, XMLHttpRequest, history, window.open, DOM URL properties, document.cookie and Web Storage so scripted URLs and state stay inside the proxy. Cacheable for 24 h.

ANY/p/{key}/{path}

Proxies a resource. Methods: GET HEAD POST PUT PATCH DELETE OPTIONS. Request bodies are streamed to the upstream.

Relay: Bare v3 and WebSocket

GET/bare/

Bare server manifest: { "versions": ["v3"], "language": "JS", … }.

ANY/bare/v3/

Compatible with the TompHTTP Bare v3 protocol, so other Bare clients can use LiteSpeed's relay and LiteSpeed's service worker can use other Bare servers. The request carries the real destination in headers; the relay performs it without following redirects:

X-Bare-URL: https://example.com/path?q=1
X-Bare-Headers: {"accept":"text/html","cookie":"a=1","user-agent":"…"}
X-Bare-Forward-Headers: accept-language        (optional: copy these from the relay request)
X-Bare-Pass-Headers: content-type              (optional: also return these as real headers)
X-Bare-Pass-Status: 304                        (optional: use these statuses as the real status)

→ 200
X-Bare-Status: 302
X-Bare-Status-Text: Found
X-Bare-Headers: {"location":"/next","set-cookie":["sid=1; Path=/"]}
(body: the remote body, streamed)

The relay decodes compressed bodies (so content-encoding is not returned) and re-compresses for the client where the adapter supports it. Errors from the relay itself use the JSON error shape below with a non-200 status and no X-Bare-Status. Timeouts apply to response headers only.

WS/api/ws?url=wss://host/path[&origin=…]

WebSocket relay (Node adapter only). Text and binary frames and close codes are piped both ways; the subprotocol the remote selects is returned to the client. The target policy and LITESPEED_ALLOWED_ORIGINS apply. The in-page runtime points proxied pages' WebSocket constructor here.

Load handling

With LITESPEED_MAX_INFLIGHT set, requests beyond the cap get an immediate 503 (code: overloaded, with Retry-After); with LITESPEED_RATE_LIMIT, a client over its rate gets 429 (rate_limited). The service worker retries idempotent requests on another relay when several are configured. Serve the relay over HTTP/2 (Cloudflare, a reverse proxy, or LITESPEED_TLS_KEY/CERT on the Node server): service-worker mode sends every sub-resource to the relay origin, and HTTP/1.1 limits browsers to 6 connections per origin.

Ad blocker

Requests are checked against Adblock Plus/uBlock-syntax filters before they leave the browser (service-worker mode) or the server (server mode, LITESPEED_ADBLOCK). A blocked request gets a typed stand-in response with X-LiteSpeed-Blocked: {rule}: empty script or stylesheet, a 1×1 GIF, a blank iframe document, or 204. Top-level navigations are never blocked. Element-hiding CSS is injected into HTML, and window.open without a user gesture returns null. A compact starter list is built in; EasyList can be added in Settings.

Request handling

  • Forwarded: all request headers except hop-by-hop and infrastructure headers (host, connection, accept-encoding, content-length, sec-*, cf-*, x-forwarded-*, via, …).
  • Referer / Origin: translated from proxy terms back to upstream terms, so CSRF and hot-link checks see the page's real origin.
  • Redirects: never followed by the server. The status is preserved and Location is rewritten, so the browser walks the chain through the proxy and cookies are applied at each hop.
  • Timeout: applies until response headers arrive (default 20 s); long downloads and streams are not cut off afterwards.
  • Runtime injection: only for navigations (Sec-Fetch-Dest absent, document, iframe or frame); HTML fetched by scripts is rewritten but not injected.

Cookies

Service-worker mode: an RFC 6265 cookie jar in the service worker (persisted in IndexedDB) handles Set-Cookie and the outgoing Cookie header per upstream, including domain/path/secure/expiry, HttpOnly (hidden from document.cookie) and the __Host-/__Secure- rules. Server mode: stateless; upstream Set-Cookie is rewritten to Path=/p/{key}/; Secure; SameSite=None; Partitioned on the relay origin and the browser does the scoping (__Host- cookies are dropped).

Errors

Navigations (Accept: text/html) receive a small HTML page; everything else receives JSON with the same HTTP status:

{ "error": { "status": 504, "code": "upstream_timeout",
             "message": "The upstream server took too long to respond.",
             "target": "https://slow.example/" } }
StatusCodeCause
400MISSING_BARE_HEADER, INVALID_BARE_HEADER, missing_url, invalid_url, unsupported_scheme, credentials_in_url, loop_detected, blocked_portBad or unsupported address
403private_target, host_blocked, host_not_allowedTarget policy (see below)

Target policy: only http/https; loopback, link-local, private and CGNAT ranges, single-label and .local/.internal names are refused. The Node adapter also resolves DNS and refuses names that point at private addresses (a small time-of-check gap remains; run it in a network without internal access for strong isolation). Optional allow/block host lists apply on top.

CORS

All responses carry CORS headers. LITESPEED_ALLOWED_ORIGINS is * by default; set it to your Pages origin (e.g. https://you.github.io) to restrict browsers to it, in which case the matching origin is echoed with credentials allowed. Preflights (OPTIONS with Access-Control-Request-Method) are answered by the backend with 204, including Access-Control-Allow-Private-Network so an HTTPS page can use a relay on localhost. Exposed headers: Server-Timing, X-LiteSpeed-Cache, X-LiteSpeed-Target, Content-Length, X-Bare-*.

Limitations

  • JS rewriting is token-level and deliberately small. eval/new Function strings, window['location'] and destructuring location out of window are not covered. Heavy SPAs may break; bot-protection and device-attestation sites generally will.
  • WebSockets need the Node relay (not Workers); WebRTC is not proxied. Service workers inside proxied pages are blocked; Workers launched by pages do not get the runtime.
  • The relay's IP address and TLS fingerprint are what sites see; sites that block them will refuse requests.
  • All proxied sites share the shell's real origin; the runtime namespaces cookies, storage and IndexedDB and the shell sandboxes the frame, but this is not a hard security boundary.
  • Service-worker mode needs HTTPS or localhost. Response size and CPU time on the relay are bounded by the host platform.

Deployment

Requirements: any runtime with the Fetch API, ReadableStream/TransformStream, TextDecoder and outbound HTTPS. Node ≥ 20 or Cloudflare Workers are supported adapters.

The frontend picks its API in this order and uses the first that answers /api/health as LiteSpeed: ?api= query parameter → saved setting → config.json (written at build time from LITESPEED_API_URL) → window.LITESPEED_API → same origin (not on github.io) → http://localhost:8787 (only when browsing from localhost). Several comma-separated relays are allowed; the service worker pins each site to one and fails over. To use a relay on your own machine from a Pages site, set its endpoint to http://localhost:8787. Step-by-step instructions are in the repository README.
